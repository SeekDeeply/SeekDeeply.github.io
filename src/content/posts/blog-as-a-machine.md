我小时候拆过一台收音机。拆完之后装回去，多出两颗螺丝，但还能响。那大概是我第一次理解"能跑"和"跑得好"之间的距离。

现在这个博客，就是一台我自己攒的机器。

## 选零件

攒机器的第一课是：**不要为用不到的性能付钱**。

博客需要什么？

- 把 Markdown 变成 HTML；
- 在浏览器里被正确地显示；
- 有一个搜索引擎能看懂的结构。

它不需要数据库（内容是文件），不需要服务端渲染（读者不需要登录），不需要 CDN 规则引擎（静态文件本来就该被缓存）。

于是我选了静态站点生成：所有页面在构建时就已经是最终的 HTML。访问一个文章页，服务器只做一件事——把一个文件发出去。

这条选择的副作用是好的：页面快到几乎没有加载过程，攻击面小到没什么可攻击的，备份就是 `git clone`。

## 装配

真正的装配工作量不在写页面，在**接口**。

- 站点级的信息（站名、签名、联系方式）只能有一个来源，任何页面都从那里取；
- 站内链接必须经过同一个函数，前缀、尾斜杠、锚点由它统一处理；
- 样式必须收敛到一组 token 上，换主题时只改变量，不动组件。

这三条约束听起来像洁癖，实际是维护成本的分水岭。当你想改一次"签名"的时候：如果只有一处，是十秒；如果有十九处，就是一个下午，而且一定会漏掉一处。

> 好的结构不是让你写得快，是让你改得动。

## 保养

机器会老化。网站的"老化"长这样：

- 依赖三个月没更新，某个包带了已知漏洞；
- 某次框架大版本升级，模板语法不再兼容；
- 一条外部链接失效了三年，没人发现；
- 图片还是三年前压缩得很差的版本。

对付老化没什么聪明办法，只能把保养变成例行公事：

1. **锁版本**。锁文件锁死依赖树，升级是一次有意识的决定，而不是一次随手的安装。
2. **每次改动都过一遍机器检查**。类型检查、构建、链接校验、产物断言，全在 CI 里跑。人的注意力会疲劳，脚本不会。
3. **让发布变便宜**。发布越便宜，你越愿意做小步修改；小步修改越多，出问题时越容易定位。
4. **写下来**。发布手册、目录约定、踩过的坑，写在 README 里。半年后的自己会感谢现在的自己。

## 折旧

所有机器都会折旧，网站也是。

区别在于：**网站的折旧主要发生在内容上，而不是代码上**。

框架可以三年不换，照样跑；但一篇文章写完放三年，它可能已经过时、片面、或者干脆是错的。这时候最该做的不是重构代码，而是回去改那篇文章。

所以我给自己的规矩是：技术栈稳定优先，内容持续修订优先。文章有 `updatedDate` 字段，改了就是改了，页面上会显示"修订于"。

## 还在转

这台机器现在每天在 GitHub 的机器上自己转一圈。我做的事只有两件：往里放东西，偶尔拧一拧螺丝。

拆收音机那年我没想过，人会长成会给自己攒机器的样子。但道理是一样的：多出两颗螺丝不要紧，要紧的是你知道它为什么能响。
