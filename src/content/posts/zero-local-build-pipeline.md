这个站点没有本地构建这一步。写一篇 Markdown，提交，推送，剩下的都交给 GitHub Actions。

不是因为我懒，而是因为**本地构建是一种容易腐烂的承诺**：我的机器上装着 Node 24、某个版本的系统库、某次临时改过的环境变量，构建能过，换一台机器就不一定。把构建交给一台每次都是全新镜像的机器，反而更接近"可复现"这三个字。

## 流水线长什么样

从推送触发到页面上线，一共六步：

1. **检出代码**，把仓库拉到 runner 上；
2. **安装依赖**，用锁文件恢复到精确版本；
3. **类型检查**，让 `astro check` 先跑一遍，语法与类型问题在这一步就报出来；
4. **构建**，生成静态 HTML、CSS、JS 与优化后的图片；
5. **建索引**，在产物上跑一遍 Pagefind，得到中文分词的全文索引；
6. **发布**，把整个目录作为 artifact 上传，再由 Pages 部署。

中间任何一步失败，后面都不会执行。这一点很重要：**发布是最后一步，而不是第一步**。

```yaml
- run: npm ci
- run: npx astro check --minimumFailingSeverity error
- run: npm run build
- run: npx pagefind --site dist
- run: node scripts/verify-dist.mjs
```

## 为什么多加一步 verify

构建成功不代表东西是对的。我见过太多次"构建通过、页面白屏"，原因无非几类：资源路径少了前缀、链接指向了不存在的文件、RSS 里的地址是相对路径。

所以第 5.5 步是一个几十行的 Node 脚本，专门做最笨的检查：

- 产物里该有的文件在不在；
- 所有站内绝对链接是不是都带了部署前缀；
- sitemap 与 RSS 里的地址是不是都能对上；
- 首页的 `lang`、`title`、`h1` 有没有丢。

它不需要任何依赖，读文件、匹配、报错、退出。但它把"上线之后才发现"挪到了"上线之前"。

> 能在 CI 里被机器发现的问题，就不要留给人眼。

## 子路径部署的坑

GitHub Pages 的项目站点会把站点放在 `/仓库名/` 下面。这意味着 `site` 要写域名，`base` 要写仓库名，而**所有以斜杠开头的站内路径都得手工补上这个前缀**。

框架不会替你补。它只会把 `base` 暴露出来，用不用是你的事。

我的做法是：模板里禁止手写 `href="/xxx"`，一律走一个 `p()` 函数。函数负责补前缀、补尾斜杠、保留锚点与查询串。只要这条规矩不破，前缀就不会漏。

## 再看一眼代价

这条流水线的代价是每次推送要等一分多钟。收益是：

- 我不需要在本地装 `node_modules`；
- 任何一台设备（甚至是手机上的网页编辑器）都能发文章；
- 构建环境永远干净，出错时可以在日志里定位到具体一步；
- 站点的可访问性、链接完整性有一道机器闸门。

一分多钟换这些，我觉得值。流水线本身就是这个站点的一部分。

如果你也想搭一个，最小可行的版本是：一个 `deploy.yml`、一个锁文件、一个检查脚本，加上"本地不构建"这条纪律。剩下的都是锦上添花。
